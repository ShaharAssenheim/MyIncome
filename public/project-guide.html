1. Overview

The Monthly Income App tracks and visualizes income grouped into three categories: Cash, Bit, and Bank Transfer. It stores transactions in a Supabase Postgres table, calculates monthly totals, displays distribution and trends, and provides an interactive UI with animation and responsive design.

High-Level Flow:
  1. User opens the app (root route /) served by app/page.tsx.
  2. Initial fetch loads all transactions from Supabase.
  3. Client-side filtering derives current month list + statistics.
  4. User adds/deletes transactions via modal & confirmation interactions.
  5. Charts & summary recompute from local state.

2. Technology Stack

Next.js 14

App Router architecture, server/client boundary, automatic code splitting, image/font optimization (not yet used), routing from app/ directory.

React 18

Modern hooks (useState, useEffect, useMemo, useCallback) for stateful UI. Potential for concurrent features & Suspense in future.

TypeScript

Static types for safety: IncomeType enum, Transaction and MonthlyStats interfaces. Improves refactors and auto-completion.

Supabase

Hosted Postgres + REST/Realtime + Auth (only DB used currently). Supabase client initialized with public URL + anon key.

TailwindCSS

Utility-first styling enabling rapid UI iteration; custom gradients and responsive classes sprinkled across components.

Framer Motion

Declarative animations: entrance transitions, hover scale effects, layout animations for transaction list.

Recharts

Data visualization: stacked bar chart for trends, pie chart for category distribution with custom tooltips.

Lucide Icons

Accessible, scalable icon set (Wallet, Smartphone, Landmark, etc.) for semantic UI cues.

RTL Locale

App root <html lang="he" dir="rtl"> supporting Hebrew and right-to-left layout.

4. Core Next.js Concepts (App Router)

  • App Directory: Routing derives from folder structure. app/page.tsx = root route.
  • Layouts: app/layout.tsx wraps all pages; use for HTML, fonts, providers, direction.
  • Server vs Client: Files with "use client" run in browser. All components here are client-side due to interactive state & Supabase JS usage.
  • Metadata Export: export const metadata = {...} centralizes SEO meta.
  • Data Fetching: Current approach: client fetch on mount. Could migrate to server actions or Route Handlers for SSR.
  • Env Exposure: Only vars prefixed with NEXT_PUBLIC_ accessible client-side.
Future SSR Opportunity: Preload initial transactions server-side to reduce first contentful paint and improve SEO if public.

interface MonthlyStats { total: number; cash: number; bit: number; bank: number; }

Notes: Both date and createdAt stored as ISO strings; transaction creation payload uses created_at (DB column) while mapping to createdAt in code for consistency.

8. State & Data Flow

  1. Raw Data: transactions state holds full dataset.
  2. Derived Month: currentMonthTransactions = transactions.filter(...).
  3. Aggregations: stats = reduce(currentMonthTransactions) generating totals.
  4. UI Bind: Cards, charts consume stats & filtered lists.
  5. Mutations: Insert/delete update Supabase then patch local state (no refetch currently).
Why Derive Locally? Minimizes DB round-trips; keeps mental model simple for beginners. Tradeoff: memory grows with dataset (could paginate later).

10. Animation Strategy (Framer Motion)

  • Interaction Feedback: Hover scale/y shifts create tactile feel.
  • List Layout: TransactionList uses AnimatePresence for smooth add/remove transitions.
  • Temporal Loading: Trends chart fakes processing time for perception management (setTimeout).
Performance Note: Excessive motion variants can impact low-end devices; consider reducing spring stiffness for accessibility.

14. Extensibility & Refactor Guidelines

Data Layer Improvements

  • Create lib/transactions.ts for fetch/insert/delete wrappers.
  • Use react-query or @tanstack/query for cache + invalidation.
  • Add optimistic updates with rollback on failure.

Domain Modeling

  • Separate raw DB shapes from UI models.
  • Introduce Result<T,E> pattern for error handling.
  • Consider zod schemas for runtime validation.

UI/Design System

  • Create reusable <Card />, <Button />, <Modal /> primitives.
  • Integrate dark mode with CSS variables.
  • Accessibility audits (focus states, ARIA labels).

Performance

  • Paginate transactions (virtual list when large).
  • Memoize heavy charts; lazy load Recharts bundle.
  • Static prefetch: server render initial dataset.

17. Authentication System (Added)

A custom JWT-based authentication layer has been added. It supports email/password and Google OAuth, short-lived access tokens (15m), refresh tokens (7–14d) stored as HttpOnly cookies, rotation on refresh, and revocation on logout.

Database Schema (Supabase)

-- Users table
  create table if not exists public.auth_users (
    id uuid primary key default gen_random_uuid(),
    email text not null unique,
    username text not null,
    password_hash text not null,
    google_id text unique,
    created_at timestamptz default now()
  );

  -- Refresh tokens table (hashed tokens)
  create table if not exists public.auth_refresh_tokens (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null references public.auth_users(id) on delete cascade,
    token_hash text not null,
    expires_at timestamptz not null,
    created_at timestamptz default now()
  );

  create index if not exists idx_auth_refresh_user on public.auth_refresh_tokens(user_id);

  -- Recommended Row Level Security policies (example skeleton)
  -- alter table public.auth_users enable row level security;
  -- alter table public.auth_refresh_tokens enable row level security;
  -- (Policies omitted for brevity; service role key used server-side.)

Service Role Key: Add SUPABASE_SERVICE_ROLE_KEY to .env.local for server-side user & token persistence (never expose to client). Client uses existing anon key only for public data (transactions).

EndpointMethodPurposeNotes
/api/auth/registerPOSTCreate new userBody: { email, username, password }. Returns access token + sets refresh cookie.
/api/auth/loginPOSTAuthenticate userBody: { email, password, stayLoggedIn }. Refresh TTL 7d or 14d based on checkbox.
/api/auth/googleGETOAuth flow & callbackNo code param: redirects to Google. With code: exchanges tokens, issues local JWTs.
/api/auth/refreshPOSTRotate refresh & new accessRequires valid refresh cookie. Returns new access token + rotated refresh cookie.
/api/auth/logoutPOSTLogout & revokeDeletes refresh cookie and revokes token (hash comparison).

Token Lifecycle

  1. Login/Register: Access (15m) returned in JSON. Refresh (7–14d) stored HttpOnly cookie.
  2. Usage: Client sends Authorization: Bearer <access> to protected routes.
  3. Expiry: On 401, client calls /api/auth/refresh to get new access + rotated refresh cookie.
  4. Logout: Revokes stored refresh token hashes & clears cookie.

Security Measures

  • Password Hashing: bcrypt (12 rounds).
  • Refresh Token Storage: Hashed before saving (prevents raw token leaks).
  • Rotation: Old refresh token revoked on refresh (protects against replay).
  • Cookie Flags: HttpOnly, Secure (production), SameSite=lax.

Client Hook

lib/auth/useAuth.ts offers login, logout, refresh, and fetchWithAuth for auto-renewing access tokens. Access token is kept only in memory (not localStorage) to reduce XSS risk.

Middleware

middleware.ts validates access tokens for routes under /api/secure/*. Adjust the matcher to protect additional paths.

Google OAuth Flow

  1. User clicks "Login with Google" which navigates to /api/auth/google.
  2. Route redirects to Google authorization endpoint.
  3. Google calls back with ?code=... to same route.
  4. Server exchanges code → Google access token, fetches profile.
  5. User created (if new). Local access + refresh tokens issued; refresh cookie set.
  6. Redirect back to /login#access_token=... to place access token in memory.
